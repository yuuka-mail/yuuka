# 前端技术选型

> yuuka 设计文档的一部分。节号沿用整份设计的全局编号，索引见 [docs/design/README.md](README.md)。

## 12. 前端技术选型

选型沿用既有项目的栈：React 19 + Vite + TS + Tailwind 4 + shadcn + TanStack Query。
理由三条：

1. **yuuka 和 arisu 将来是并肩使用的两个界面**（§11.1 的人格分层），
   同一套设计语言和组件才能让"系统在说"和"agent 在说"用同一组视觉 token 表达
2. 既有项目多数落在这个栈上，熟练度与组件复用度最高；单人长期维护的项目里这条权重最大
3. shadcn 是 copy-in 不是依赖——组件进自己仓库，十年项目不会被上游牵着走

```
React 19 + Vite + TypeScript + Tailwind 4 + shadcn/ui + TanStack Query
+ TanStack Virtual（虚拟列表）+ vite-plugin-pwa
```

### 12.0 Next 还是 Vite：选 Vite

Next 和 Vite 在既有项目里都在用，**所以这里没有熟悉度成本**，
可以纯按项目特性定。按特性定的结果是 Vite：

- **要 `go:embed` 进单个二进制**。Next 的价值集中在 SSR / RSC / server actions /
  middleware / image optimization，而 `output: 'export'` 会把这些全部关掉——
  等于付了 Next 的复杂度却拿不到它的好处
- **登录后才有内容，没有 SEO 和首屏需求**。SSR 在这个项目里不解决任何问题
- **依赖面和构建时间**。十年尺度的自用项目，上游升级噪音是真实成本，
  Next 的 major 升级历来比 Vite 吵

反过来说，什么情况该回头选 Next：如果哪天 WebUI 不再 embed 而是独立部署
（比如挂到 Cloudflare Pages 上，给手机当入口），那 Next 的价值就回来了。
但那和 §3.1 的"单二进制、数据在自己机器上"是相反的方向，暂时不考虑。

shadcn 对 Vite 的支持没有问题（它本来就是 copy-in 的组件源码，不绑框架脚手架），
既有项目里已有 Vite + shadcn 的组合，配置可直接沿用。

### 12.1 砍掉的两块复杂度

**一、不引富文本编辑器，撰写用 Markdown。**
ProseMirror / Lexical / TipTap 任意一个都会带进一整套生态和长期升级义务。
而开发者自用邮箱里 Markdown 更顺手，引用回复用 `>` 天然贴合邮件传统。
发送时在 Go 侧生成 `text/plain` + `text/html` 两份（§10.2 本来就是我们自己组装 MIME，
具体规则见 §10.2.1）。

编辑器定 **CodeMirror 6**（模块化、框架无关）：要的是 Markdown 高亮、软换行、
`>` 引用的自动续行、粘贴图片转附件这几件事，textarea 全都得自己补。
M2 第一周用 textarea 占位可以，但别让粘贴和快捷键逻辑长在 textarea 上，
否则迁移时要重写。

**二、通知区不渲染原始 HTML，直接复用 agent 的结构化视图。**
§8.1 已经为 agent 做了 `text/agent`：去样式、去 tracking pixel、
保留结构、带稳定锚点。通知区要的恰好就是"一眼看到码"，
**所以它和 agent 消费同一份数据**——省掉一整套渲染逻辑，而且人和 agent
看到的内容天然一致，不会出现"agent 说有码但界面上没有"。

### 12.2 邮件正文的两条渲染路径

| 区 | 渲染方式 | 远程资源 | 锚点 |
|---|---|---|---|
| 通知区（机器邮件） | 结构化视图（§8.1）直接渲染成 DOM | 不加载 | ✓ 可定位 |
| 会话区（人类邮件） | `<iframe sandbox srcdoc>` + CSP | 默认阻断，点击才经自己的代理放行 | ✗ |

**重要约束：`yuuka://message/<id>#part/2/para/7` 只在结构化视图上成立。**
iframe 里是原信自己的 HTML，我们无法在其中挂稳定 id。所以 agent 的引用
（§8.5 的 `cites`）默认指向结构化视图；人想看原样时再切到 iframe。
这一条必须在实现前说清，否则锚点会在会话区悄悄失效。

`sandbox` 不要加 `allow-scripts`。邮件 HTML 永远是不可信输入（§8.3），
而 catch-all 意味着任何人都能投递它。

附件是第三条路径，而且不渲染：一律作为下载返回（`Content-Disposition: attachment`、`nosniff`、
`sandbox` CSP），不做预览。附件里的 HTML、SVG、PDF 都可能带脚本，预览器就是新的攻击面；
需要预览时再单独设计（M1 的落法见 §12.7）。

### 12.3 几个必选的单点

| 需求 | 选择 | 理由 |
|---|---|---|
| 列表 | **TanStack Virtual** | catch-all 的机器邮件是几万条量级，虚拟滚动不是优化而是前提 |
| 服务器状态 | **TanStack Query** | 缓存失效/重试这些坑别自己踩 |
| 实时增量 | 原生 `EventSource` + `since_state` 游标（§8.6） | 收到事件后 invalidate 对应 query key，不全量重拉 |
| 类型同源 | **OpenAPI 3.1**（从 Go 类型生成，§5.1）→ `openapi-typescript` + `openapi-fetch` + `openapi-react-query` | 手写 TS 类型必然和 Go 漂移，漂移在邮件这种字段多的模型里尤其痛；请求参数和端点配对也要进契约，光生成响应类型不够 |
| 界面文案 | **Paraglide JS** + inlang 项目格式（§12.11） | 编译成带类型的函数，键和参数写错是类型错误；文案是仓库里的 JSON，锁定小 |
| 产物 | `go:embed web/dist` | dev 时 Vite dev server，API 走 Vite proxy 到 Go |

组件库的边界要认清：邮件客户端 UI 高度特化（三栏布局、虚拟列表、线程视图、
前缀聚合），**shadcn 只能提供基础件**（Dialog / Command / Dropdown / Toast），
列表区和阅读区都得自己写。不要指望组件库解决布局。

### 12.4 PWA 顺带解决"本地客户端"

`vite-plugin-pwa` + IndexedDB 缓存最近 N 封 → **WebUI 装到手机上即是自有客户端**。
这直接影响路线图：§6 的 M4 里"自己的客户端"不需要另写，
**JMAP 的优先级因此下降**——它从"我自己客户端的前提"退回成"对外协议"
（给第三方工具、给将来的 IMAP 网关用）。

一个要贯穿下来的策略：浏览器缓存是**又一份数据副本**，
所以 `sync_policy=metadata` 的工作邮箱（§9.2）不该缓存到 IndexedDB。
账户级策略必须一路传到前端缓存层，不能只在后端生效。

### 12.5 agent 面板的视觉分层

§11.1 要求"系统在说"和"agent 在说"一眼可分。实现上这是**两套设计 token**
（颜色、图标、署名位），不是两种文案口吻：

- `system` / yuuka：事实陈述——新信到达、出口失败、配额告警、正则提取的验证码
- `agent:arisu`：推测与提案——摘要、分类建议、起草的回复，**必须带 `cites` 锚点**

提案卡片就地长在邮件旁（而不是另开聊天框），接受/拒绝是一等按钮，
接受后可勾选"以后同类自动处理"→ 落成 `rules`（§8.5）。

### 12.6 前端的分期

- **M1**：三栏骨架 + 虚拟列表 + 前缀聚合 + 结构化阅读 + 搜索。
  **不做** iframe 渲染，**不做**撰写器——会话区要等 M2 的发信能力
- **M2**：iframe 阅读 + Markdown 撰写 + 回复引用 + 身份选择器（默认取自 delivery）
  + 会话区按线程列、已读状态（§12.9）
- **M3**：界面 i18n（§12.11，先于本阶段的其他界面）+ 提案卡片 + 规则编辑 + 前缀泄漏视图（已落地）+ 通知区的码位填上提取值（已落地）、改判（§12.9）
  + 管理动作放进上下文，「设置」页只做查看与收紧（§12.12）
- **M4**：PWA + IndexedDB 离线

### 12.7 M1 的落法

M1 的 WebUI（`web/`）和它读的 REST（`internal/api`），以及设计里没写死、实现时定下的几处：

- **REST 只读、按路由声明 scope**。端点和各自要的 scope 写在 [`internal/api/api.go`](../../internal/api/api.go)
  的 `routes` 一张表里，ACL 测试和 `openapi.json` 都从这张表来（§5.1），漏一条测试就失败。投递事实（信封、认证结果）另要
  `delivery:read`，没有就不给，结构化视图里的 `facts.delivered_to` 和 `facts.auth` 同理（标 `withheld`，§8.1）。
  消息列表和搜索用 `(received_at, id)` 键集游标而不是 offset，是因为新信到达时 offset 分页会重复或跳行
- **附件只下载，不渲染**（§8.3、§12.2），实现见 [`internal/api/attachment.go`](../../internal/api/attachment.go)。
  按 Viewer 取信、原件只从可见的投递读（§13.8）；什么算附件只由解析器的判定决定，和视图里列出的同源，
  正文和内嵌图片不算。几条取舍：
  - 字节只解传输编码，不做字符集转换——下载的是发件人附上的原样文件；解不开就报错，而不是给一个悄悄变短的文件
  - 文件名去掉路径、控制字符和双向格式字符（防 `txt.exe` 显示成 `exe.txt`），保留扩展名
  - 响应头一律按下载处理（`attachment`、`nosniff`、沙箱 CSP、`no-store`）。`Content-Type` 只对少数
    打开时不执行脚本的常见格式照用声明值，其余一律 `application/octet-stream`：反正不会内联显示，
    类型只影响保存下来的文件被系统认成什么；HTML、SVG、XML、脚本和 `text/*`（声明的字符集可能是错的）都不在内
  - 每次下载记一条 `actions`（谁、哪封、哪个 part、字节数；不记内容和文件名），记不下来就不给下载
  agent 侧还没有对应的 MCP 工具，`get_message` 里附件仍标「此处不可读」
- **API 层是生成的**（§5.1）：`web/src/api/schema.gen.ts` 由 `openapi.json` 生成，`client.ts` 在它上面建
  openapi-fetch 客户端和 openapi-react-query 的 hook，路径、参数和响应都有类型；`types.ts` 只给 schema 起名字。
  非 2xx 一律在中间件里变成 `ApiError`（`detail` 当消息，`code` 供分支），TanStack Query 只看到这一种错误。
  查询键是 `[method, path, init]`，401 时把会话查询置空、回到登录页
- **页面壳不需要会话**。`go:embed` 的 `index.html` 对任何非文件路径都返回（`no-store`），
  哈希命名的 `assets/` 缓存一年；壳加载后再同源 `fetch /auth/session`，401 就原地显示登录，
  URL 不变，所以从 TG 链接点进来、登录后直接落在那封信上。视图状态全部在 query string 里
  （`area` `prefix` `dg` `q` `m`，`a`：打开的信里的锚点，以及 M2 撰写和外发用的几项，见 [`web/src/mail/view.ts`](../../web/src/mail/view.ts)），不引路由库
- **`web/dist/` 只跟踪 `.gitkeep`**，让新克隆不先构建前端也能编译 Go；这样的二进制对页面请求回 503
  并提示先构建前端。代价是 Vite 不能清空输出目录，改为构建前只删 `dist/assets`
- **CSP** 是 `default-src 'none'` 加 self 的脚本、样式、图片、连接，`frame-ancestors 'none'`。
  M2 加 iframe 时在这里开 `frame-src`
- **登录页不链接恢复入口**（§13.7：恢复码不出现在日常登录路径上）；`/recover` 换到令牌后直接跳
  `/enroll#<token>`。`/enroll` 读完片段立刻从地址栏抹掉；没有令牌但有会话时，它变成「再加一把 passkey」
- **系统声音与 agent 声音**（§12.5）落成 `--system-*` / `--agent-*` 两组 token 和一个
  `Voice` 组件：颜色、标记形状（方 / 圆）、署名都不同。M1 只有系统在说：阅读区的认证结果、警告、
  剥掉了什么、接收时间是 yuuka 的事实陈述（结构化视图的 `facts`），与信头自称的 `Date` 分开显示。
  `dmarc=fail` 和隔离是错误色、带边框；未验证和降级是警告色，都排在事实框最上面
- **阅读区渲染结构化视图**（§12.1），和 agent 的 `get_message` 是同一棵树：信头和线程条仍取
  `messages/{id}`，正文和事实取 `messages/{id}/view?level=part`，按 `more` 分段续取
  （`web/src/mail/reading-data.ts`），`reading-body.tsx` 把块渲染成 DOM，块的锚点就是 DOM id。
  `?m=<id>&a=part/1/para/3` 打开时滚到那一块并高亮，不在第一段里就自动续取到它出现为止；
  悬停块左侧的 ¶ 把锚点写进地址栏并复制 `yuuka://` URI。正文一律是文本节点，不用
  `dangerouslySetInnerHTML`；链接 `rel="noopener noreferrer"`、不带 referrer，旁边显示真实主机名
  （punycode 原样显示），链接文字自称的主机和真实主机对不上时标成错误色。附件列表里每项是指向上面那个端点的普通下载链接，不预览。
  取舍：引用折叠后只剩一行标记，看不到被引的原文——那是线程里的另一封信，点线程条去看
- **shadcn 选 Base UI 作底层**（`components.json` 的 `base-nova`），只拷了 Button / Input / Badge /
  ToggleGroup / Skeleton / Separator；三栏、列表、阅读区按 §12.3 自己写
- **lint 用 oxlint 而不是 ESLint**：仓库固定 TypeScript 7（与 Worker 一致），typescript-eslint
  还不支持它；oxlint 不依赖 TS 的 JS API，一个依赖就带齐 React hooks 规则。typescript-eslint
  支持 TS 7 之后可以换回去，规则集不变
- **开发**：Vite 开发服务器把 `/api`、`/auth` 代理到一个本地的 `yuuka serve`（任务与端口见
  [`mise.toml`](../../mise.toml)）；那个 `serve` 配置的 WebUI origin 要设成 Vite 的地址，WebAuthn 和跨源检查才认。
  [`internal/devseed`](../../internal/devseed/) 把合成语料和生成的变体灌进开发库；
  [`web/scripts/screenshots.mjs`](../../web/scripts/screenshots.mjs) 用 Chrome 的虚拟认证器走完注册和登录，
  截亮、暗、窄屏三套图

### 12.8 设计基线

WebUI 是工具，不是展示面：一天打开几十次，每次几秒——扫一眼列表、看一个码、读一封信。
基线是为这件事定的几条规则。数值在 [`web/src/index.css`](../../web/src/index.css)，这里只写为什么。

- **颜色只表意。** 界面框架一律中性灰；屏幕上出现色相，只能是五种意思之一：
  键盘焦点或锚点指到的块（`ring`，蓝）、需要留意（`warning`）、出错（`destructive`）、
  系统在说（`system`，青）、agent 在说（`agent`，紫）。所以选中态是更深的中性灰，
  而不是浅色强调色——M1 最初的选中色和 `system` 的青挨得太近，打开的信看起来像系统在说话。
  链接靠下划线区分，不另占色相。代价是界面整体偏素，将来要有品牌色也只能留在 logo 上
- **字号按角色分五档**：meta 11 / small 12 / ui 13 / body 14 / title 18（px）。
  Tailwind 自带的字号在主题里清空了，[`web/src/design.test.ts`](../../web/src/design.test.ts)
  拦住旧名字和任意值，写新代码时得先想清楚「这段字是什么角色」。
  11px 会被通用的设计检查报成「字太小」，这是有意的：它只给时间、计数、收件前缀、主机名这类
  扫一眼就够的元信息，正文从不低于 14px。层级优先用字重和 `muted-foreground` 拉开，不再加档。
  信里的各级标题都是 body 字号加粗：结构化视图本来就去了样式，标题放大会和信的主题抢层级
- **密度**：4px 网格。控件高 24 / 28 / 32（紧凑的工具条用 28），顶栏 44，
  列表行 56（发件人一行、主题一行，虚拟列表按定高算），前缀侧栏行 28。新的列表类组件沿用这几个高度
- **图标跟字号**：meta、small 配 12px，ui 配 14px，body 和按钮配 16px
- **状态**：悬停是 `muted`；选中是 `accent`，全宽的行再加一道 2px 前景色竖线
  （侧栏的圆角条只换底色）；锚点指到的块是 `ring` 的淡底加细框，它说的是「你是被带到这里的」，
  和选中是两回事。降级的信改用 `muted-foreground`，不降透明度——降透明度会把对比度一起降到不可读。
  分段切换（草稿、外发的筛选，窄屏的会话 / 通知）是例外：按下的段反相成 `primary` 底、`primary-foreground` 字，
  没按下的段悬停才是 `muted`。段只有 24px 高、几个字宽，`accent` 的淡底在这么小的面积上和悬停、和没按下分不开；
  反相仍是中性灰，不占色相。代价是它比行的选中态重，所以只给这种几个字的小控件用
- **只用系统字体。** 中文 webfont 动辄数 MB，只引拉丁字体又和旁边回退的中文对不上。
  具名字体排在 `system-ui` 前面，因为 Linux 上 `system-ui` 多半解析成 DejaVu Sans，
  而 Noto Sans CJK 自带的拉丁字形好得多。等 CJK 字体能按需切片到百 KB 级再回头看
- **不加动效**，shadcn 基础件自带的颜色过渡除外

不在基线里的是信息架构：通知区和会话区怎么分、前缀侧栏怎么应对成千上万个地址、
事实框在一切正常时收成多大。这些不靠调样式解决，见 §12.9。

### 12.9 信息架构

先按任务定架构。打开 yuuka 的理由按频率排：

1. **拿码**：验证码、magic link，几十秒内用完就丢。主入口是 TG（§8.4），WebUI 是第二入口
2. **读人写的信、回信**（回信从 M2 起）
3. **清理机器信**：按服务看，批量收掉
4. **检查**：降级的信、未认领的前缀、仿冒、泄漏。频率低，但关乎安全，必须找得到

搜索横跨所有任务。M1 的界面是一个通用三栏邮箱加一个分类筛选，四类任务挤在同一张列表里，
1 和 2 互相打扰。

#### 两个区是两个视图，不是一张列表里的两种行

- **会话区** = `human` + `unknown`，**通知区** = `machine`（§3 原则 4），另留一个「全部」入口给浏览式查找。
  降级的信（§4.3）两区都不显示，只在「检查」里出现
- 分成两个视图，是因为两区的列表形状、打开方式、「处理完」的含义都不一样：会话区按线程列、
  点开来读，已读未读有意义；通知区一条一行、多数不用点开，码会过期，处理完是「收掉」而不是「读过」。
  混排的结果是：要么会话被机器信淹没，要么码被线程分组藏起来
- **`unknown` 归会话区：分类出错时，往人看得见的方向错。** 机器信误进会话区只是多一行噪声，
  人写的信误进通知区可能就错过了。代价是规则成熟之前会话区会混进陌生的机器信；
  改判是一等操作，改一次就生成规则（M3）。分类可靠以后，可以回头把 `unknown` 单独列出来
- 默认落在会话区。码的主入口是 TG，打开 WebUI 多半是为了读信

#### 通知区：码是一行的主角

- 按时间平铺，前缀只做筛选，不分组：要码时要的是「刚到的那封」，按服务分组反而得先找组；
  要按服务清理时，点侧栏里的前缀就是按服务看
- 行仍是 56px 两行（§12.8）：第一行是发件方、收件前缀、时间；第二行有提取值时显示提取值
  （等宽加粗，旁边是复制按钮和「n 分钟内有效」），没有时是主题和摘要，就是现在的样子。过期的码变灰，不消失
- 提取值是 yuuka 断言的事实，按系统声音呈现（§12.5）。`dmarc=fail` 的信已经降级、不在这里；
  未验证的信照样显示提取值，但旁边标警告色的「未验证」——仿冒的验证码信不该把码摆在最显眼的地方而不加说明
- 提取在 M3（§6）。值从内容派生，能被 reparse 重建（§4.2）。在那之前这个位置显示主题：版面先定，内容后到
- **M3 的落法**（[`extracted-line.tsx`](../../web/src/mail/extracted-line.tsx)，纯函数在
  [`extracted.ts`](../../web/src/mail/extracted.ts)）：列表摘要带 `extracted`（最好的码、最好的链接、到期时间），
  第二行依次是系统色的方形标记、码（等宽、body 字号加粗）、复制按钮、「7 min left」、可能的「unverified」，最后是灰色的主题——
  码旁边仍看得到是哪封信。没有码只有链接时显示「open 主机名 ↗」：一个普通链接，新标签页打开，
  `rel="noopener noreferrer"`、不带 referrer；主机名取浏览器真正会去的那个（punycode 原样），从不自动打开、不预取。
  倒计时在前端每 15 秒按本地时钟重算，服务端给的 `expired` 只是取数那一刻的结论。
  只有 `machine` 的行显示提取值，在哪个列表里都一样（「全部」、按前缀看）；会话区里人写的信即使带一串数字也照旧显示主题。
  「unverified」看的是 `sender_verified`：可信接收方报了 `dmarc=pass` 才算证明了发件域，
  这是认证事实，没有 `delivery:read` 的会话拿不到它，也就不标。
  行从 `<button>` 改成可聚焦的 `role="option"`，因为复制按钮和链接要嵌在行里，按钮里不能再套按钮；
  Enter / 空格照样打开这封信，复制和链接的点击不冒泡成「打开」。
  搜索结果里是通知的那几行（`machine`）同样带提取值，搜索跨两区时码在哪一行都一样显眼；别的命中不带，它们是按字找到的。
  阅读区在事实框下面多一行系统声音的小框（署 yuuka，码、复制、倒计时、「unverified」），
  只给通知：从 TG 链接点进来的人第一眼要的是码，不是正文。
  分类和码位用同一个判断（§3 原则 4）：分类器读提取器，所以码位里有码的信就在通知区，不会留在会话区
- 处理完就收起（归档，标注层动作，可撤销，§8.2），可以按前缀批量收起。M2 有写路径之前只有时间衰减

#### 会话区：按线程列

- 一行一个线程：参与者、主题、最新一封的摘要和时间、封数。打开是线程视图
- 已读未读只在会话区有意义，未读加粗。状态存在 `message_state.flags`，是决定而不是派生（§4.2）
- 要一个按线程分页的列表端点，随 M2 一起做；在那之前仍是一行一封信

#### 侧栏是注意力的入口，不是地址目录

- 从上到下：会话 / 通知 / 全部 / 草稿 / 外发（M2，§12.10）；已认领的前缀；检查
- 已认领的前缀按字母序排，位置稳定，靠记忆找；带标签。一个给出去的地址一行，几十到上百行，列得下；
  超过一屏时顶部出一个筛选框，输入即过滤
- **未认领的前缀不逐个列出。** catch-all 遇到字典攻击会有成千上万个，§3.3 本来就要求它们静默登记。
  侧栏只在「检查」里给一个计数，点进去是一张按最近到达排序的列表，点一项看它的信；
  认领在界面上从 M3 起，之前用 CLI。侧栏只取已认领的前缀（`state=claimed`），未认领的分页取
  （`state=discovered`，`limit` / `offset`）：这张表变化慢、只给人翻，offset 分页够用，不必像消息列表那样用游标
- 「检查」组：降级的信、未认领的前缀、泄漏与仿冒（§3.3）。后者合成一项「Leaks & spoofs」，
  数的是有问题的**前缀**而不是信：泄漏是地址层面的事，同一个泄漏了的地址收到第二十封信不是第二十件事。
  点进去是这些前缀按最近一次出事排序的列表，每行写泄漏 / 仿冒数和不在期望里的发件域，点一项看它的信。
  泄漏和仿冒没有拆成两项：数量都很小，拆开只多一行；仿冒用 `destructive`、泄漏用 `warning` 区分
- 已认领的前缀出过事时，侧栏那一行在计数前多一个圆点：有仿冒是 `destructive`，只有泄漏是 `warning`。
  选中这个前缀时，列表顶部是一块按系统声音写的前缀事实：给了谁（`expected_domains`）、DMARC 证实过的发件域
  （不在期望里的标警告色）、泄漏 / 仿冒数，以及最近几封出事的信，点开即读。没出事时它只有一两行，
  没写期望时提示 `yuuka prefix expect`。实现在 [`web/src/mail/leaks.tsx`](../../web/src/mail/leaks.tsx)，
  数据来自前缀表和 `GET /api/v1/prefixes/{address}`
- 会话 / 通知 / 全部三项不带数字：总封数不指向任何该做的事，M2 有了已读状态再换成未读数。
  带数字的是「检查」组（还有多少要看）和每个前缀（量突然变了本身就是信号）
- 多账户（M3.5）时账户是筛选条件，不是侧栏的顶层目录：§9 要的是统一视图
- 窄屏上，会话 / 通知是列表顶部的两段切换，其余收进侧栏按钮

#### 事实框：正常时一行，出事时整框

- 可信接收方给出 `dmarc=pass`、没有降级、没有任何警告时，事实框收成信头下的一行，
  仍署 yuuka、带方形标记，例如「yuuka · dmarc=pass example.com · 收到 19:13」，点开是完整的框
- 有任何错误或警告（`dmarc=fail`、未验证、降级、隔离、泄漏、仿冒）时整框展开，排在正文前面。
  泄漏 / 仿冒的判定（§3.3）在框里是一行「Prefix」：收件前缀、`ok` / `leak` / `spoof`、所指的域；
  仿冒按错误、泄漏按警告。判定是 `ok` 的信仍收成一行，行尾多一句「expected sender」。判定在
  [`web/src/mail/facts.ts`](../../web/src/mail/facts.ts) 的 `isQuiet`；结构化视图还没取到时先显示只有接收时间的那一行，
  这样占多数的正常信打开时不会先闪出一个整框
- 理由：每封信都摆一个同样大的框，读的人很快就学会跳过它，真出事的那次也一起跳过。平时安静，是为了出事时被看见。
  剥掉了什么（tracking pixel 之类）属于展开后才看的细节

#### 不变的

- `?m=` 和 `?a=` 已经是「点进来直接落在这封信、这一段上」的链接（§12.7），保持不变；
  其余视图参数是内部的，这次 `class` 换成了 `area`
- agent 的提案卡片（M3，§12.5）在阅读区里、长在信旁边，两个区一样
- 搜索跨两区，来自通知区的结果带一个标记
- 这里要新增的读路径（线程列表、分页的前缀表、计数）都带 `Viewer`，进 ACL 测试表（§13.8）：
  受限主体看到的计数也只能算它看得见的信

#### 分期

- **已落地**（M1 的数据够用）：两个区作为视图、侧栏重排、「检查」组和未认领前缀表、
  事实框收起。消息列表的 `class` 参数接受逗号分隔的多个值，服务端不知道「区」这个概念，
  区只是前端对分类的组合（[`web/src/mail/view.ts`](../../web/src/mail/view.ts) 的 `listParams`）
- **M2**：会话区按线程列、已读状态、通知的收起（需要写路径）
- **M3**：改判、在界面上认领前缀；提取值填进码位已落地（见上）；泄漏视图已落地（期望域仍由 CLI 写，界面只读）

### 12.10 M2 的撰写与外发

撰写器、草稿、outbox 三个视图建在这几组端点上，路径、参数、响应以 [`openapi.json`](../../internal/api/openapi.json) 为准，
handler 在 [`internal/api/sending.go`](../../internal/api/sending.go)；界面在 [`web/src/send/`](../../web/src/send/)，
措辞和状态到语气的映射集中在 [`outgoing.ts`](../../web/src/send/outgoing.ts)（纯函数，有测试）。这里只写为什么是这个形状：

- **信息架构**（§12.9）：侧栏顶组在「全部」下面加「草稿」「外发」两项，不另开顶层导航。草稿的计数是还能改的草稿数，
  外发的计数只数 `unknown`（警告色）：只有它在等一个人的决定，排队中、已发出都不需要人做什么。
  外发要 `delivery:read`（里面有 Bcc），会话没有这个 scope 就不显示这一项。撰写器占阅读区那一栏，
  和打开一封信是同一个位置；顶栏有「Compose」，阅读区有「Reply」，键盘是 `c` / `r`。
  视图状态仍在 query string 里：`compose=1` 是新信、`reply=<id>` 是回复、`d=<id>` 是草稿、`o=<id>` 是 outbox 行、
  `st` 是草稿或 outbox 列表的筛选（[`view.ts`](../../web/src/mail/view.ts)）
- **自动保存**：第一次有改动时 `POST` 建草稿，之后防抖 `PUT` 整份；保存排成一条链，建草稿之前不会有 `PUT` 抢跑。
  建好以后地址栏换成 `d=<id>`，撰写器不重新挂载（字段已经在里面，正在打字）。只打开一个回复、什么都没改，
  不建草稿——草稿列表里不该出现没人写过一个字的东西。按发送时没有草稿就先建
- **身份选择器**：新信从 `GET /api/v1/identities`，回复从 `reply-identities`（第一项是默认，取自原信进来的地址，§9.3）。
  选项文字里带「sends (auto)」或「held: owner cap」，选中项下面一行是 yuuka 署名的预览：「Send queues it · auto · to any recipient · 10/hour」
  或「Held as a draft: drafts only」加服务端的 `hold_detail` 原文。原因的短语按 `hold_reason` 定，不按 `hold_detail` 的文字分支——
  后者是给人看的，会改。`*@zone` 这种模式身份要再填本地部分，因为 From 只能是地址。
  `sends` 只是预览：收件人范围和限额在提交时才算，所以「会发出」可能变成停在草稿，反过来不会。
  自己的草稿 From 用的身份不在 `/identities` 里（档位 none）时，预览和下面「agent 写的草稿」一样取草稿上的 `identity_owner`：
  属于另一个人就写「Held: only bob can send as this address」，否则写「Held as a draft: no grant」和它属于谁；
  选择器里保留这个地址作为一项并标上同样的话，不让下拉框显示成列表里的第一个身份——那会让人以为 From 是别的地址。
  这里只是把服务端会做的决定提前说出来，不多出任何发信的路
- **停在草稿是正常结果**（§8.9）：提交返回 `queued: false` 时，表单上方出一个系统声音的框，写原因和「什么都没发出」，
  草稿留着，可以改了再发。原因只说一次：From 下面的预览行若要说的是同一个原因，就不再出现；
  owner 封顶时框里直接写只有谁能确认。不弹错误框、不用错误色。`queued: true` 时表单变只读，框里是 outbox 这一行的事实，
  状态还会自己变（排队、发送、重试）时每 3 秒轮询一次，到终态停
- **agent 写的草稿**：列表行和撰写器标题旁是 agent 的圆点和名字，撰写器顶部是 agent 署名的框（写于何时、`cites` 指向哪封信哪一段），
  正文左边一道 agent 色的竖线——这段文字是 agent 写的。人按的按钮叫「Confirm and send」，预览行写「Send confirms arisu's draft」：
  人确认代替档位（§8.9 规则 2），所以这里不显示人自己的档位预览，From 也不让改。身份属于另一个人时，预览直接写只有 owner 能确认。
  owner 取自草稿上的 `identity_owner`，不从 `/identities` 查：查看者在这个身份上的档位是 none 时，那里没有它
- **错误按 `code` 说**（§5.1）：每个 `code` 一句固定的话，`detail` 只在 `invalid_body` / `no_identity` / `submission_rejected` 这类
  指名了具体字段或地址的 code 后面跟着显示；`code` 本身以等宽小字附在后面，方便对照日志
- **发出的信在列表里**：消息摘要、搜索命中和线程条上的 `outgoing` 显示成一个小标记（发出图标加「queued」「sent」「may have been sent」「not sent」），
  颜色按意思：已送达用系统色，需要看一眼的用警告色，没发出用错误色，正在走的用灰。阅读区里只发出、没收回来过的信，
  事实框不再说「unverified」：认证一行写「none: sent by this system, never received」，另有一行「Sent: by this system as me@example.com · queued」，
  时间标成「Submitted」。状态不需要人（排队、发送、已发出）时事实框照样收成一行；`unknown`、失败、部分送达时整框展开，带「Open in outbox」
- **阅读区的收件人**：发件人下面一行是 To / Cc / Reply-To，有显示名的写名字加灰色地址，每个字段超过三个就收成「+n more」。
  它们是信头里写的，和发件人一样未经验证；信实际到了哪个地址是下面「delivered to」那一行（投递事实）。
  只发出的信没有投递，这一行是唯一能看到发给了谁的地方。地址由详情端点在取信时从可读那一路的原件解析（§13.8），
  不读 0007 存的折叠地址：那几列为线程通信方匹配而存，丢了大小写和显示名（§4）
- **outbox**：列表行第一行是主题、状态、时间，第二行是每个收件人和它自己的状态——部分送达一眼就看得出来。
  From 跟在主题后面，放得下就整个显示，放不下就整个不显示（详情里有）：截成几个字母的地址什么也说明不了，手机上几乎总是这样。
  收件人放不下时先让后面的收件人收成省略号，第一个收件人和它的状态保持可读。不是人提交的行在主题后带 agent 的圆点和名字（§12.5）
  outbox 表没有主题列，主题在 Sent 副本里：`OutboxEntry.subject` 由 store 在读行时从 Sent 副本的消息取，可见性和行本身是同一个条件（§13.8）。
  `unknown` 的详情下面是三个选项，每个旁边写清代价：
  「It was sent」（记成收下）、「Send it again」（可能让对方收到两封，选中时按钮变成错误色并重复这句话）、「Give up」（记成没发出）。
  选一个、再按一次才提交。只有 human 主体且带 `submission:send` 的会话看得到这三个选项，其余只看到一句「只有人能决定」
- **编辑器仍是 textarea**（§12.1 定的是 CodeMirror）：除了 Ctrl+Enter 发送，没有任何粘贴和按键逻辑长在它上面，换编辑器时不必重写。
  不做 Markdown 预览：预览要一个 Markdown 渲染器，渲染结果又要进 DOM；在有理由加依赖之前，发出去的样子以 Sent 副本为准

### 12.11 界面语言

界面文字现在写死在组件里，是英文。i18n 放在 M3 之前做（§6）：成本和文案条数成正比，M1、M2 留下的约一百条挪一次就完；
M3 的提案卡片、规则编辑、改判是文案最多的一批，先写死再抽等于写两遍。

**只翻译界面自己说的话。**

- 不翻邮件内容；不翻 `text/agent` 结构化视图和 MCP 的工具描述——它们是给 agent 的数据，措辞要稳定（§8.1）；
  `code`、scope、状态值这类标识符照原样显示
- 服务端写给人看的文字（problem+json 的 `detail`、`hold_detail`）不翻，也不当主句：界面按稳定的 `code` / `hold_reason`
  选一句自己的话，`detail` 只作附注原样显示。发信界面已经这样做（§12.10「错误按 `code` 说」），
  读路径还在直接显示服务端的文字，要改成同一个做法。这样服务端不需要知道界面语言，API 不做 `Accept-Language` 协商
- 发出的信里由系统生成的文字跟身份走，不跟界面走：读它的是收件人，不是正在点按钮的人，而且发出去就不可变（§3.1）。
  组装（§10.2.1）目前不生成任何自然语言文字；将来要加引用头、转发头时，语言是身份上的设置

**用 Paraglide JS + inlang，不手写。** 最初的打算是一个带类型的 TS 字典加平台的 `Intl`，几十行。放弃它是因为
i18n 是边角情况积累很深的领域：复数类别、带参数的语序、富文本里链接放在句子哪里、语言协商与回退、
字典随文案增长的体积……手写版本在两种语言下看起来都没问题，问题要等到第三种语言或第一个外部译者才暴露，
那时文案已经长在几百个调用点上了。一个被广泛使用的实现把这些坑踩过了（见 AGENTS.md「品味」里对依赖的三问）。
在几个成熟实现里选 Paraglide，因为它的形状和这个项目一致：

- **编译期生成，不是运行时字典。** 文案放在 `web/messages/<locale>.json`，由编译器生成带类型的 ESM 函数（`m.unread({ count })`），
  键和参数写错就是类型错误；没用到的文案被 tree-shake 掉。运行时只有生成的代码，Paraglide 本身是构建期依赖
- **锁定小。** 文案是仓库里的普通 JSON，项目配置是 `project.inlang/settings.json`（开放格式，翻译工具能直接读）；
  上游哪天不维护了，生成出来的代码照样能跑，换掉它是重写编译这一步，调用点 `m.*` 可以不动。这是「十年后它还在吗」的答案：
  它不必还在
- **复数、数字、日期走平台的 `Intl`**（Paraglide 的 declaration formatter 包了 `Intl.PluralRules` / `NumberFormat` / `DateTimeFormat`），
  不另带一套 locale 数据
- 和 Vite 是一个插件的事；SvelteKit 官方的 i18n 集成就是它，React + Vite 是它示例里的一等公民

几处要落实的：

- **生成物要先于类型检查。** `web` 的 `check` 先编译文案再跑 `tsc`，和 `openapi-typescript` 的 `gen --check` 一个位置
- **漏翻不会编译失败**（类型按消息生成，不按语言），所以 `check` 里要有一条测试对照各语言的消息键；
  运行时漏翻退回英文，不显示空白或键名
- **富文本**（句子中间有链接、强调）用 `@inlang/paraglide-js-react` 的类型化 markup，不把 HTML 拼进文案：
  译者决定链接在句子哪里，组件决定它怎么渲染

**英文是源语言和回退，中文是第一份译文。** 这是公开项目，英文文案对外部贡献者没有门槛；
回退到英文意味着漏翻的那条仍然可读。语言的取法是 Paraglide 的 strategy `["localStorage", "preferredLanguage", "baseLocale"]`：
用户在界面上选过就用它，否则取浏览器语言，都没有就是英文。存在浏览器里、不进数据库：
它是这台设备上的偏好，不是主体的属性，等多端同步偏好有了真实需求再说。
切换语言按 Paraglide 的默认整页重载，不用 `reload: false`——那会把所有响应式更新交给应用自己做；
切语言是很少做的动作，撰写中的内容有草稿自动保存兜着（§12.10）

**对设计基线（§12.8）的影响：**

- `<html lang>` 跟界面语言走；邮件正文的容器不继承它。`lang` 决定汉字取哪套字形，界面是中文时，
  一封日文信不该按中文字形排。正文有 `Content-Language` 就用它，没有就是 `lang=""`（未知）
- 列表时间是为扫一列定的（[`format.ts`](../../web/src/lib/format.ts)）：今天是时分、今年是月日、更早是 `YYYY-MM-DD`。
  只有中间那档随语言变（`Nov 1` / `11月1日`），列宽按最宽的语言留
- 截图自查从「亮暗两套主题 × 窄屏」再乘上两种语言。英文通常更长，按钮和分段控件以英文为准不截断
- 消息要有人守门：JSX 文本节点里的裸字符串由测试拦住，办法和 [`design.test.ts`](../../web/src/design.test.ts) 拦字号一样，
  否则新代码会悄悄绕过 `m.*`

### 12.12 管理动作长在上下文里

§13.10 把管理动作分成三类：信任根只在 CLI；跟着信走的决定进界面；权限类配置在界面上只能看和收紧。落到界面上：

- **不开独立的「管理后台」区。** 侧栏是注意力的入口（§12.9），管理不是一个要定期去巡视的地方。
  单独一个后台，会把决定和引出它的那封信拆开
- **跟着信走的决定出现在引出它的地方**：
  - 前缀事实框（§12.9）里认领、取消认领、编辑期望域；未认领前缀表的每一行可以直接认领。
    这样事实框就不必再提示 `yuuka prefix expect`
  - 读信时「以后这类信……」用这封信的发件人、`List-Id` 和收件前缀起一份规则草稿；
    保存前先给出回溯会命中多少封，和 `yuuka rule apply --dry-run` 走同一个计算
  - `unknown` 外发的裁决已经在 outbox 详情里（§12.10）；改判按 §12.9 放在阅读区
- **「设置」是唯一不跟着信的页面**，从顶栏的账户菜单进，不进侧栏。里面放的是没有天然对应哪封信的东西：
  passkey、凭据、身份与授权、规则列表
  - 凭据、身份、授权一页列全，每一项都能吊销、调低或删除。要放宽的地方，用系统声音（§12.5）写出对应的 CLI 命令，
    不放一个灰掉的按钮：告诉人去哪做，比灰掉更有用
  - 收紧也要确认一次，但不弹模态框：和 outbox 的裁决一样，选一项、再按一次才提交，旁边写清代价，
    例如「arisu 的下一次调用会失败」
