# 分诊：用决策模型判断垃圾、欺诈与分区

> yuuka 设计文档的一部分。节号沿用整份设计的全局编号，索引见 [docs/design/README.md](README.md)。

## 15. 分诊

catch-all 收件箱的垃圾和欺诈是一等问题（§4.3、§7）。传统做法是关键词、正则、
贝叶斯和规则集（rspamd 一类）：要人维护词表和训练语料，换个说法、换种语言的钓鱼信就认不出来。
§4.3 的最低实现只靠认证结论和前缀状态，§3 原则 4 的分区靠头部信号，
两者都答不了「这封陌生人的信是不是在骗我」。

带类型的决策模型改变了成本：问一个封闭问题（选一个、是非、打分），一次前向得到校准过的概率，
不生成文本。Jev（托管）、Laya 和 Kev（开源，可本地跑）共用同一个 `POST /v1/systemone` 协议，
小的检查点在 CPU 上也能跑。对个人信箱每天几十到几百封的量，每封信都问一遍是负担得起的。
所以本节把它放进决策链路，代价是要先回答它在链路里是什么、能做什么、错了怎么办。

### 15.1 三层：确定信号、决策模型、agent

| 层 | 是什么 | 何时跑 | 产出 | 能决定什么 |
|---|---|---|---|---|
| 确定信号 | `internal/classify`、可信接收方的认证结论、前缀状态（§3.3） | ingest 当场 | 派生列或投递事实 | §3 原则 4 的分区、§4.3 的降级 |
| 决策模型 | 一个打分服务，System One 协议 | ingest 提交之后，异步，每封都跑 | 评分（§15.2），一种观测事实 | 只作用于被评分的这一封（§15.4） |
| agent | 外部主体（§8），走 MCP | 按需，主要看决策模型拿不准的信 | 提案、可撤销的标注（§8.2、§8.5） | 经人接受后沉淀成规则 |

分工的理由：确定信号便宜、可复现，但只认得格式；agent 能读懂上下文，但每封信都让它推理一遍太贵，
而且它要读不可信正文、还能调工具。决策模型夹在中间：每封都看得起，没有工具，输出是几个概率，
被注入也只能改这几个数。它拿不准的信（落在阈值之间，§15.5）才交给 agent，
这正是这类模型自己声称的用法——在 LLM 介入之前先过滤一遍。

### 15.2 评分是观测事实

§4.2 的标准是「同样的输入、任何时候重算都得到同样的结果」。模型评分不满足：
换一个模型版本、换一句问法，同一封信的分数就变了。所以它不是派生；它也不是任何人的决定。
它和 `deliveries.spf_recheck` 是同一类：**某个时刻、某个评分器对这封信的观测**，算一次、存下来。

- 存在单独的表里（暂名 `model_scores`），一行是一个问题的一次回答：消息 id、评分器（配置里的名字）、
  模型与版本、问题集版本、问题键、各选项概率、是否弃权、评分时刻。
  键挂在 message id 上，它跨 reparse 稳定（§4.2）
- **不写 `messages.spam_score`**：`messages` 是派生表，reparse 会重写它；
  那一列留给将来可能有的、从原件确定算出的垃圾分
- reparse 不碰评分。重新评分是一个显式动作（换了模型或问题集之后），写新行、不删旧行：
  「上个月那封信为什么被藏起来」要能用当时的评分回答
- 输入是 §8.1 的 agent 视图：`facts` 那一半（认证结论、投递前缀是否认领、是否首次来信、
  From 显示名和域名、Reply-To 是否换了域）加 `content` 那一半（包在不可信边界里）。
  欺诈判断最有用的恰恰是这些事实，单看正文的模型做不好「自称银行、但 dmarc=fail」这件事。
  事实会变（前缀之后被认领），所以评分行记下它用的是哪一刻的事实；超出模型上下文的正文截断，并记下截断了
- 评分是关于内容的信息，读它走 store 的 `Viewer`（§13.8），进 ACL 测试表：
  看不到这封信头部的主体，也看不到它的评分

### 15.3 问什么

问题集是数据，带版本；改一句问法就是新版本，新旧分数不放在一起比。初版：

| 键 | 类型 | 问的是 |
|---|---|---|
| `kind` | 选择 | 通知 / 会话 / 营销 / 垃圾 |
| `phishing` | 是非 | 是否冒充他人，诱导点击、提供凭据或付款 |
| `injection` | 是非 | 是否含有写给 AI 助手的指令 |
| `needs_reply` | 是非 | 是否需要本人回复 |

`kind` 和 §3 原则 4 的 machine / human 不是一回事：前者回答「这是什么」，后者是 UI 的分区。
`phishing` 和垃圾属于另一条轴——可信与否，它的落点是 §4.3 的降级，不是分区。
前缀泄漏检测（§3.3）看的是地址，这里看的是内容，两者互补，不互相替代。

### 15.4 评分能做什么

评分**只能作用于被评分的这一封信**，而且一切可撤销：

- 可以：把这封信降级（§4.3 的同一套效果：不推送、不进聚合视图、不进泄漏基线）、
  打警告、在 agent 视图的 `facts` 里列出评分，供 agent 和外发审核参考
- 不可以：
  - **泛化**：评分本身永远不变成规则，v1 的规则也不引用评分（§15.7）；
    从示例信生成候选条件时同样不从评分泛化——评分随发件人写的内容走，和主题、正文一样
  - **放松确定的检查**：「模型说不是钓鱼」不能撤销 `dmarc=fail` 的降级，
    不能让外发审核放行（§8.9 的模型审核只能升级，这里同理），也不能把认证状态从「未验证」改成别的
  - 删除原件、跟随链接（§8.2 的越界级别，对谁都不给）

为什么允许它直接降级，却不允许 agent 的规则这么做（§8.5 要人接受）：发件人能影响的只有
**自己那封信**的分数。把自己的垃圾做得像正常信，是垃圾过滤一直在打的仗，输了只是漏掉一封垃圾；
把别人的正常信推进垃圾区，发件人做不到，因为那封信的内容不归他写。规则不一样：
一条被注入诱导出来的「以后来自某地址的都归档」会作用到攻击者碰不到的信上。

误判的代价落在被藏起来的正常信上，所以：

- 原件不可变（§3.1），降级不删任何东西，人的改判永远压过评分
- 降级区写明原因（哪个问题、概率多少、哪个模型），一键改判
- **默认保护**：投递到已认领前缀、`dmarc=pass`、发件人以前来过信的信，评分只打标、不降级——
  这里误判最贵（往往就是在等的验证码），是垃圾的概率又最低
- 评分署名既不是 yuuka（系统事实）也不是 arisu（agent 的推测），见 §15.8

**降级在读时现算，不经规则。** §4.3 的降级本来就不存储，由投递的认证结论和前缀状态在查询时算出
（`notDowngraded`，[`content.go`](../../internal/store/content.go)）；模型降级接在同一处。
一封信因模型而降级，当且仅当：处在执行模式、某个问题的最新评分越过了它的动作阈值、
没有一条投递属于上面的受保护范围、人没有对这封信改判过。
§4.3 的降级按投递算（任一投递不降级则信不降级），模型降级按信算，两者任一成立，信就降级。
现算的好处和认领前缀一样：阈值调整、从影子模式切到执行模式都当场生效，也当场撤回，
不需要回溯运行，也不需要 `revert`。

**改判是逐封的人的决定。** §4.3 的降级靠认领前缀纠正，模型降级没有这个抓手，
所以 `message_state` 要多一个「是垃圾 / 不是垃圾」的改判，和 class、archived、标签一样经
`annotation_log` 写入（§8.5），同时就是 §15.5 的标注数据。它有方向：agent（等级 2）只能标「是垃圾」，
不能标「不是垃圾」——agent 读的是不可信正文，凭内容判断放松降级正是本节禁止的事。
标注核心现在只按等级判断，这个方向限制要另加。

**推送有上限地等评分。** 推送在 ingest 内容步骤之后异步发出（[`ingest.go`](../../internal/ingest/ingest.go)），
评分比它更晚，不等的话垃圾在被判出来之前就推到了 TG。所以开着评分器且处在执行模式时，
推送的那个后台任务先等这封信的评分，上限可配（默认几秒），到了就按上面的规则重算降级，再决定推不推：

- 超时或评分器出错就照常推送，失败时放行：多一条垃圾推送只是噪音，评分器一挂就收不到验证码才是事故
- 受保护的信不等：模型本来降级不了它们，而在等的验证码大多就是这一类
- 影子模式下不等：分数不触发动作，没必要加延迟
- 规则的 `off` / `silent` 照旧生效；规则和模型都只能把推送调低（§8.5）
- 超时之后才判出的垃圾，已发出的推送不撤回；等待期间进程崩溃的信不再推送，
  和「补跑永不推送」同一个口径。没有评分的信由补跑循环补评分（§15.6）

评分不放进 webhook 的请求里同步做：提交点之后已经不会丢信，但没有理由拉长 Worker 的等待。

### 15.5 校准与上线

厂商的校准不能直接拿来用：Laya 的 README 说发布的检查点偏自信、要用自己的数据拟合，
Kev 每个检查点只带一个温度。分布不同，换到别人的收件箱，「0.9」不一定还是 0.9。所以分两步上线：

1. **影子模式**（默认）：每封都评分，评分显示出来、进 agent 视图，但不触发任何动作
2. 运维者按问题设动作阈值，之后才开始降级。阈值是配置，不是代码；两个阈值之间是弃权带，
   落在里面的信什么都不做，留给 agent 看

人的改判就是标注数据：yuuka 可以按问题报告「评分 ≥ 阈值的信里，人改回来的比例」，
运维者据此调阈值，而不是只信厂商的 benchmark。偏差要心里有数：人只改判自己看到的信，
被藏起来没人看的那些不会产生标注，所以这个比例偏乐观。

### 15.6 接入：一个协议，后端可换

- Go 侧是消费方定义的一个小接口，加一个 `POST /v1/systemone` 的 HTTP 客户端，只用标准库，
  不加依赖。这个协议已经有三个实现，后端换哪家都不改代码；要是哪天协议本身没了，
  要改的也只是这一个客户端
- **默认关闭**。不配评分器，系统的所有功能照旧，只是没有评分。评分器不可用时不重试到天荒地老：
  没有当前版本评分的信由补跑循环找出来再判（和 `ProcessBacklog` 找缺列的行一个写法，§4.2），
  并发和速率有上限，永远不挡 ingest，也不进 Worker
- 后端（数字都是各项目自报，未在本项目的语料上复现）：

| 后端 | 形态 | 取舍 |
|---|---|---|
| [Laya](https://github.com/NandhaKishorM/laya) | 编码器，3–4 亿参数；有多语言检查点 | CPU 能跑，适合没有 GPU 的服务器；多语言检查点对中文信件是必要的 |
| [Kev](https://github.com/jaredpalmer/kev) | Qwen 底座，0.8B–27B | 小的要小显卡或 Apple Silicon，大的要数据中心 GPU；准确率随尺寸上去 |
| Jev（TypeSafe 托管） | 云端 API | 自报最准、校准最好；**信件内容离开部署环境**，只能由运维者显式开启 |

- 默认只连本机或同一部署环境里的评分器。托管后端要单独的开关，运维文档要写明内容会发给第三方

### 15.7 与其他章节的关系

- §4.3：「需要更强判定时旁路 rspamd」不再是计划中的下一步。rspamd 的长处
  （RBL 信誉、模糊哈希、成熟的规则集）这里不覆盖，以后真需要时它仍可以作为另一个评分来源；
  但内容判断交给决策模型
- `internal/classify` 保留：它是 ingest 当场、零依赖、可复现的那一层。评分不改 machine / human 分区，
  `kind` 只作为证据进 agent 视图和 UI
- §8.5 的规则：**v1 的规则不引用评分**。规则在 ingest 的内容步骤里、按到达时的同一份快照求值，
  评分那时还没有。另一种做法是让引用评分的规则等评分到了再跑，但那会让同为等级 1 的后跑规则
  不顾优先级覆盖先跑的，破坏「同一份快照、按优先级第一条命中的赢」；要保住语义就得把整套规则推迟到评分之后，
  又丢掉「崩溃不会留下规则没跑的投递」。代价是「被判为钓鱼的信打某个标签」这类规则现在写不了；
  真有这个需要时，再考虑把整套规则推迟到评分之后（有上限地等，和推送一样）。
  规则已有的 `verdict` 字段（`leak` / `spoof`）是读路径确定算出的结论，和本节的模型评分无关
- §8.1：agent 视图的 `facts` 增加评分（问题、概率、模型、时刻），和认证结论一样是给 agent 的证据
- §8.9：回复的线程里有信被判为 `injection` 或 `phishing` 时，`review` 档升级到人。只收紧
- §8.6：评分写完记一条 `changes`，长期在跑的 agent 由此知道有新的、模型拿不准的信要看

### 15.8 未定

- **评分以谁的名义显示**。§11.1 只有两种声音：系统事实和 agent 的推测。评分是推测，但不是 arisu 的；
  是给它一个 `service:` 主体、借用 agent 那套 token 再加概率，还是单独一套 token，要在做 UI 时定
- **表结构**。迁移只追加，`model_scores` 的列落地之前要再过一遍；落地后这一节换成指向迁移的链接
- **「是垃圾 / 不是垃圾」改判的存法**（§15.4）：`message_state` 加列、`annotation_log` 认这个字段，
  都是迁移；和方向限制一起定
- 附件进不进评分输入（初版不进）
- 多主体（§13）下阈值是全局的还是按主体的
