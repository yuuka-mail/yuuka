# 前端技术选型

> yuuka 设计文档的一部分。节号沿用整份设计的全局编号，索引见 [docs/README.md](README.md)。

## 12. 前端技术选型

选型沿用既有项目的栈：React 19 + Vite + TS + Tailwind 4 + shadcn + TanStack Query。
理由三条：

1. **yuuka 和 arisu 将来是并肩使用的两个界面**（§11.1 的人格分层），
   同一套设计语言和组件才能让"系统在说"和"agent 在说"用同一组视觉 token 表达
2. 既有项目多数落在这个栈上，熟练度与组件复用度最高；单人长期维护的项目里这条权重最大
3. shadcn 是 copy-in 不是依赖——组件进自己仓库，十年项目不会被上游牵着走

```
React 19 + Vite + TypeScript + Tailwind 4 + shadcn/ui + TanStack Query
+ TanStack Virtual（虚拟列表）+ vite-plugin-pwa
```

### 12.0 Next 还是 Vite：选 Vite

Next 和 Vite 在既有项目里都在用，**所以这里没有熟悉度成本**，
可以纯按项目特性定。按特性定的结果是 Vite：

- **要 `go:embed` 进单个二进制**。Next 的价值集中在 SSR / RSC / server actions /
  middleware / image optimization，而 `output: 'export'` 会把这些全部关掉——
  等于付了 Next 的复杂度却拿不到它的好处
- **登录后才有内容，没有 SEO 和首屏需求**。SSR 在这个项目里不解决任何问题
- **依赖面和构建时间**。十年尺度的自用项目，上游升级噪音是真实成本，
  Next 的 major 升级历来比 Vite 吵

反过来说，什么情况该回头选 Next：如果哪天 WebUI 不再 embed 而是独立部署
（比如挂到 Cloudflare Pages 上，给手机当入口），那 Next 的价值就回来了。
但那和 §3.1 的"单二进制、数据在自己机器上"是相反的方向，暂时不考虑。

shadcn 对 Vite 的支持没有问题（它本来就是 copy-in 的组件源码，不绑框架脚手架），
既有项目里已有 Vite + shadcn 的组合，配置可直接沿用。

### 12.1 砍掉的两块复杂度

**一、不引富文本编辑器，撰写用 Markdown。**
ProseMirror / Lexical / TipTap 任意一个都会带进一整套生态和长期升级义务。
而开发者自用邮箱里 Markdown 更顺手，引用回复用 `>` 天然贴合邮件传统。
发送时在 Go 侧生成 `text/plain` + `text/html` 两份（§10.2 本来就是我们自己组装 MIME，
具体规则见 §10.2.1）。

编辑器定 **CodeMirror 6**（模块化、框架无关）：要的是 Markdown 高亮、软换行、
`>` 引用的自动续行、粘贴图片转附件这几件事，textarea 全都得自己补。
M2 第一周用 textarea 占位可以，但别让粘贴和快捷键逻辑长在 textarea 上，
否则迁移时要重写。

**二、通知区不渲染原始 HTML，直接复用 agent 的结构化视图。**
§8.1 已经为 agent 做了 `text/agent`：去样式、去 tracking pixel、
保留结构、带稳定锚点。通知区要的恰好就是"一眼看到码"，
**所以它和 agent 消费同一份数据**——省掉一整套渲染逻辑，而且人和 agent
看到的内容天然一致，不会出现"agent 说有码但界面上没有"。

### 12.2 邮件正文的两条渲染路径

| 区 | 渲染方式 | 远程资源 | 锚点 |
|---|---|---|---|
| 通知区（机器邮件） | 结构化视图（§8.1）直接渲染成 DOM | 不加载 | ✓ 可定位 |
| 会话区（人类邮件） | `<iframe sandbox srcdoc>` + CSP | 默认阻断，点击才经自己的代理放行 | ✗ |

**重要约束：`yuuka://message/<id>#part/2/para/7` 只在结构化视图上成立。**
iframe 里是原信自己的 HTML，我们无法在其中挂稳定 id。所以 agent 的引用
（§8.5 的 `cites`）默认指向结构化视图；人想看原样时再切到 iframe。
这一条必须在实现前说清，否则锚点会在会话区悄悄失效。

`sandbox` 不要加 `allow-scripts`。邮件 HTML 永远是不可信输入（§8.3），
而 catch-all 意味着任何人都能投递它。

附件是第三条路径，而且不渲染：一律作为下载返回（`Content-Disposition: attachment`、`nosniff`、
`sandbox` CSP），不做预览。附件里的 HTML、SVG、PDF 都可能带脚本，预览器就是新的攻击面；
需要预览时再单独设计（M1 的落法见 §12.7）。

### 12.3 几个必选的单点

| 需求 | 选择 | 理由 |
|---|---|---|
| 列表 | **TanStack Virtual** | catch-all 的机器邮件是几万条量级，虚拟滚动不是优化而是前提 |
| 服务器状态 | **TanStack Query** | 缓存失效/重试这些坑别自己踩 |
| 实时增量 | 原生 `EventSource` + `since_state` 游标（§8.6） | 收到事件后 invalidate 对应 query key，不全量重拉 |
| 类型同源 | **`tygo`**（Go struct → TS）挂 `go:generate` | 手写 TS 类型必然和 Go 漂移，漂移在邮件这种字段多的模型里尤其痛 |
| 产物 | `go:embed web/dist` | dev 时 Vite dev server，API 走 Vite proxy 到 Go |

组件库的边界要认清：邮件客户端 UI 高度特化（三栏布局、虚拟列表、线程视图、
前缀聚合），**shadcn 只能提供基础件**（Dialog / Command / Dropdown / Toast），
列表区和阅读区都得自己写。不要指望组件库解决布局。

### 12.4 PWA 顺带解决"本地客户端"

`vite-plugin-pwa` + IndexedDB 缓存最近 N 封 → **WebUI 装到手机上即是自有客户端**。
这直接影响路线图：§6 的 M4 里"自己的客户端"不需要另写，
**JMAP 的优先级因此下降**——它从"我自己客户端的前提"退回成"对外协议"
（给第三方工具、给将来的 IMAP 网关用）。

一个要贯穿下来的策略：浏览器缓存是**又一份数据副本**，
所以 `sync_policy=metadata` 的工作邮箱（§9.2）不该缓存到 IndexedDB。
账户级策略必须一路传到前端缓存层，不能只在后端生效。

### 12.5 agent 面板的视觉分层

§11.1 要求"系统在说"和"agent 在说"一眼可分。实现上这是**两套设计 token**
（颜色、图标、署名位），不是两种文案口吻：

- `system` / yuuka：事实陈述——新信到达、出口失败、配额告警、正则提取的验证码
- `agent:arisu`：推测与提案——摘要、分类建议、起草的回复，**必须带 `cites` 锚点**

提案卡片就地长在邮件旁（而不是另开聊天框），接受/拒绝是一等按钮，
接受后可勾选"以后同类自动处理"→ 落成 `rules`（§8.5）。

### 12.6 前端的分期

- **M1**：三栏骨架 + 虚拟列表 + 前缀聚合 + 结构化阅读 + 搜索。
  **不做** iframe 渲染，**不做**撰写器——会话区要等 M2 的发信能力
- **M2**：iframe 阅读 + Markdown 撰写 + 回复引用 + 身份选择器（默认取自 delivery）
  + 会话区按线程列、已读状态（§12.9）
- **M3**：提案卡片 + 规则编辑 + 前缀泄漏视图 + 通知区的码位填上提取值、改判（§12.9）
- **M4**：PWA + IndexedDB 离线

### 12.7 M1 的落法

M1 的 WebUI（`web/`）和它读的 REST（`internal/api`），以及设计里没写死、实现时定下的几处：

- **REST 只读、按路由声明 scope**。端点和各自要的 scope 写在 [`internal/api/api.go`](../internal/api/api.go)
  的 `routes` 一张表里，ACL 测试遍历这张表，漏一条测试就失败。投递事实（信封、认证结果）另要
  `delivery:read`，没有就不给，结构化视图里的 `facts.delivered_to` 和 `facts.auth` 同理（标 `withheld`，§8.1）。
  列表用 `(received_at, id)` 键集游标而不是 offset，是因为新信到达时 offset 分页会重复或跳行
- **附件只下载，不渲染**（§8.3、§12.2），实现见 [`internal/api/attachment.go`](../internal/api/attachment.go)。
  按 Viewer 取信、原件只从可见的投递读（§13.8）；什么算附件只由解析器的判定决定，和视图里列出的同源，
  正文和内嵌图片不算。几条取舍：
  - 字节只解传输编码，不做字符集转换——下载的是发件人附上的原样文件；解不开就报错，而不是给一个悄悄变短的文件
  - 文件名去掉路径、控制字符和双向格式字符（防 `txt.exe` 显示成 `exe.txt`），保留扩展名
  - 响应头一律按下载处理（`attachment`、`nosniff`、沙箱 CSP、`no-store`）。`Content-Type` 只对少数
    打开时不执行脚本的常见格式照用声明值，其余一律 `application/octet-stream`：反正不会内联显示，
    类型只影响保存下来的文件被系统认成什么；HTML、SVG、XML、脚本和 `text/*`（声明的字符集可能是错的）都不在内
  - 每次下载记一条 `actions`（谁、哪封、哪个 part、字节数；不记内容和文件名），记不下来就不给下载
  agent 侧还没有对应的 MCP 工具，`get_message` 里附件仍标「此处不可读」
- **类型由 `tygo` 生成**，覆盖哪些 Go 文件见 [`internal/api/tygo.yaml`](../internal/api/tygo.yaml)；
  前端检查先 `go generate` 再类型检查，Go 侧改了字段 TS 立刻报错
- **页面壳不需要会话**。`go:embed` 的 `index.html` 对任何非文件路径都返回（`no-store`），
  哈希命名的 `assets/` 缓存一年；壳加载后再同源 `fetch /auth/session`，401 就原地显示登录，
  URL 不变，所以从 TG 链接点进来、登录后直接落在那封信上。视图状态全部在 query string 里
  （`prefix` `class` `dg` `q` `m`，以及 `a`：打开的信里的锚点），不引路由库
- **`web/dist/` 只跟踪 `.gitkeep`**，让新克隆不先构建前端也能编译 Go；这样的二进制对页面请求回 503
  并提示先构建前端。代价是 Vite 不能清空输出目录，改为构建前只删 `dist/assets`
- **CSP** 是 `default-src 'none'` 加 self 的脚本、样式、图片、连接，`frame-ancestors 'none'`。
  M2 加 iframe 时在这里开 `frame-src`
- **登录页不链接恢复入口**（§13.7：恢复码不出现在日常登录路径上）；`/recover` 换到令牌后直接跳
  `/enroll#<token>`。`/enroll` 读完片段立刻从地址栏抹掉；没有令牌但有会话时，它变成「再加一把 passkey」
- **系统声音与 agent 声音**（§12.5）落成 `--system-*` / `--agent-*` 两组 token 和一个
  `Voice` 组件：颜色、标记形状（方 / 圆）、署名都不同。M1 只有系统在说：阅读区的认证结果、警告、
  剥掉了什么、接收时间是 yuuka 的事实陈述（结构化视图的 `facts`），与信头自称的 `Date` 分开显示。
  `dmarc=fail` 和隔离是错误色、带边框；未验证和降级是警告色，都排在事实框最上面
- **阅读区渲染结构化视图**（§12.1），和 agent 的 `get_message` 是同一棵树：信头和线程条仍取
  `messages/{id}`，正文和事实取 `messages/{id}/view?level=part`，按 `more` 分段续取
  （`web/src/mail/reading-data.ts`），`reading-body.tsx` 把块渲染成 DOM，块的锚点就是 DOM id。
  `?m=<id>&a=part/1/para/3` 打开时滚到那一块并高亮，不在第一段里就自动续取到它出现为止；
  悬停块左侧的 ¶ 把锚点写进地址栏并复制 `yuuka://` URI。正文一律是文本节点，不用
  `dangerouslySetInnerHTML`；链接 `rel="noopener noreferrer"`、不带 referrer，旁边显示真实主机名
  （punycode 原样显示），链接文字自称的主机和真实主机对不上时标成错误色。附件列表里每项是指向上面那个端点的普通下载链接，不预览。
  取舍：引用折叠后只剩一行标记，看不到被引的原文——那是线程里的另一封信，点线程条去看
- **shadcn 选 Base UI 作底层**（`components.json` 的 `base-nova`），只拷了 Button / Input / Badge /
  ToggleGroup / Skeleton / Separator；三栏、列表、阅读区按 §12.3 自己写
- **lint 用 oxlint 而不是 ESLint**：仓库固定 TypeScript 7（与 Worker 一致），typescript-eslint
  还不支持它；oxlint 不依赖 TS 的 JS API，一个依赖就带齐 React hooks 规则。typescript-eslint
  支持 TS 7 之后可以换回去，规则集不变
- **开发**：Vite 开发服务器把 `/api`、`/auth` 代理到一个本地的 `yuuka serve`（任务与端口见
  [`mise.toml`](../mise.toml)）；那个 `serve` 配置的 WebUI origin 要设成 Vite 的地址，WebAuthn 和跨源检查才认。
  [`internal/devseed`](../internal/devseed/) 把合成语料和生成的变体灌进开发库；
  [`web/scripts/screenshots.mjs`](../web/scripts/screenshots.mjs) 用 Chrome 的虚拟认证器走完注册和登录，
  截亮、暗、窄屏三套图

### 12.8 设计基线

WebUI 是工具，不是展示面：一天打开几十次，每次几秒——扫一眼列表、看一个码、读一封信。
基线是为这件事定的几条规则。数值在 [`web/src/index.css`](../web/src/index.css)，这里只写为什么。

- **颜色只表意。** 界面框架一律中性灰；屏幕上出现色相，只能是五种意思之一：
  键盘焦点或锚点指到的块（`ring`，蓝）、需要留意（`warning`）、出错（`destructive`）、
  系统在说（`system`，青）、agent 在说（`agent`，紫）。所以选中态是更深的中性灰，
  而不是浅色强调色——M1 最初的选中色和 `system` 的青挨得太近，打开的信看起来像系统在说话。
  链接靠下划线区分，不另占色相。代价是界面整体偏素，将来要有品牌色也只能留在 logo 上
- **字号按角色分五档**：meta 11 / small 12 / ui 13 / body 14 / title 18（px）。
  Tailwind 自带的字号在主题里清空了，[`web/src/design.test.ts`](../web/src/design.test.ts)
  拦住旧名字和任意值，写新代码时得先想清楚「这段字是什么角色」。
  11px 会被通用的设计检查报成「字太小」，这是有意的：它只给时间、计数、收件前缀、主机名这类
  扫一眼就够的元信息，正文从不低于 14px。层级优先用字重和 `muted-foreground` 拉开，不再加档。
  信里的各级标题都是 body 字号加粗：结构化视图本来就去了样式，标题放大会和信的主题抢层级
- **密度**：4px 网格。控件高 24 / 28 / 32（紧凑的工具条用 28），顶栏 44，
  列表行 56（发件人一行、主题一行，虚拟列表按定高算），前缀侧栏行 28。新的列表类组件沿用这几个高度
- **图标跟字号**：meta、small 配 12px，ui 配 14px，body 和按钮配 16px
- **状态**：悬停是 `muted`；选中是 `accent`，全宽的行再加一道 2px 前景色竖线
  （侧栏的圆角条只换底色）；锚点指到的块是 `ring` 的淡底加细框，它说的是「你是被带到这里的」，
  和选中是两回事。降级的信改用 `muted-foreground`，不降透明度——降透明度会把对比度一起降到不可读
- **只用系统字体。** 中文 webfont 动辄数 MB，只引拉丁字体又和旁边回退的中文对不上。
  具名字体排在 `system-ui` 前面，因为 Linux 上 `system-ui` 多半解析成 DejaVu Sans，
  而 Noto Sans CJK 自带的拉丁字形好得多。等 CJK 字体能按需切片到百 KB 级再回头看
- **不加动效**，shadcn 基础件自带的颜色过渡除外

不在基线里的是信息架构：通知区和会话区怎么分、前缀侧栏怎么应对成千上万个地址、
事实框在一切正常时收成多大。这些不靠调样式解决，见 §12.9。

### 12.9 信息架构

先按任务定架构。打开 yuuka 的理由按频率排：

1. **拿码**：验证码、magic link，几十秒内用完就丢。主入口是 TG（§8.4），WebUI 是第二入口
2. **读人写的信、回信**（回信从 M2 起）
3. **清理机器信**：按服务看，批量收掉
4. **检查**：降级的信、未认领的前缀、仿冒、泄漏。频率低，但关乎安全，必须找得到

搜索横跨所有任务。M1 的界面是一个通用三栏邮箱加一个分类筛选，四类任务挤在同一张列表里，
1 和 2 互相打扰。

#### 两个区是两个视图，不是一张列表里的两种行

- **会话区** = `human` + `unknown`，**通知区** = `machine`（§3 原则 4），另留一个「全部」入口给浏览式查找。
  降级的信（§4.3）两区都不显示，只在「检查」里出现
- 分成两个视图，是因为两区的列表形状、打开方式、「处理完」的含义都不一样：会话区按线程列、
  点开来读，已读未读有意义；通知区一条一行、多数不用点开，码会过期，处理完是「收掉」而不是「读过」。
  混排的结果是：要么会话被机器信淹没，要么码被线程分组藏起来
- **`unknown` 归会话区：分类出错时，往人看得见的方向错。** 机器信误进会话区只是多一行噪声，
  人写的信误进通知区可能就错过了。代价是规则成熟之前会话区会混进陌生的机器信；
  改判是一等操作，改一次就生成规则（M3）。分类可靠以后，可以回头把 `unknown` 单独列出来
- 默认落在会话区。码的主入口是 TG，打开 WebUI 多半是为了读信

#### 通知区：码是一行的主角

- 按时间平铺，前缀只做筛选，不分组：要码时要的是「刚到的那封」，按服务分组反而得先找组；
  要按服务清理时，点侧栏里的前缀就是按服务看
- 行仍是 56px 两行（§12.8）：第一行是发件方、收件前缀、时间；第二行有提取值时显示提取值
  （等宽加粗，旁边是复制按钮和「n 分钟内有效」），没有时退回主题。过期的码变灰，不消失
- 提取值是 yuuka 断言的事实，按系统声音呈现（§12.5）。`dmarc=fail` 的信已经降级、不在这里；
  未验证的信照样显示提取值，但旁边标警告色的「未验证」——仿冒的验证码信不该把码摆在最显眼的地方而不加说明
- 提取在 M3（§6）。值从内容派生，能被 reparse 重建（§4.2）。在那之前这个位置显示主题：版面先定，内容后到
- 处理完就收起（归档，标注层动作，可撤销，§8.2），可以按前缀批量收起。M2 有写路径之前只有时间衰减

#### 会话区：按线程列

- 一行一个线程：参与者、主题、最新一封的摘要和时间、封数。打开是线程视图
- 已读未读只在会话区有意义，未读加粗。状态存在 `message_state.flags`，是决定而不是派生（§4.2）
- 要一个按线程分页的列表端点，随 M2 一起做；在那之前仍是一行一封信

#### 侧栏是注意力的入口，不是地址目录

- 从上到下：会话 / 通知 / 全部；已认领的前缀；检查
- 已认领的前缀按字母序排，位置稳定，靠记忆找；带标签。一个给出去的地址一行，几十到上百行，列得下；
  超过一屏时顶部出一个筛选框，输入即过滤
- **未认领的前缀不逐个列出。** catch-all 遇到字典攻击会有成千上万个，§3.3 本来就要求它们静默登记。
  侧栏只在「检查」里给一个计数，点进去是一张表，按最近到达和封数排序，可以在那里认领
  （M3 起；M1 用 CLI）。现在 `GET /api/v1/prefixes` 一次返回全部前缀，这张表上线时要分页，
  侧栏只取已认领的和未认领的计数
- 「检查」组：降级的信、未认领的前缀；M3 加「可能泄漏」「可能仿冒」
- 多账户（M3.5）时账户是筛选条件，不是侧栏的顶层目录：§9 要的是统一视图
- 窄屏上，会话 / 通知是列表顶部的两段切换，其余收进侧栏按钮

#### 事实框：正常时一行，出事时整框

- 可信接收方给出 `dmarc=pass`、没有降级、没有任何警告时，事实框收成信头下的一行，
  仍署 yuuka、带方形标记，例如「yuuka · dmarc=pass example.com · 收到 19:13」，点开是完整的框
- 有任何错误或警告（`dmarc=fail`、未验证、降级、隔离）时整框展开，排在正文前面，和现在一样
- 理由：每封信都摆一个同样大的框，读的人很快就学会跳过它，真出事的那次也一起跳过。平时安静，是为了出事时被看见。
  剥掉了什么（tracking pixel 之类）属于展开后才看的细节

#### 不变的

- `?m=` 和 `?a=` 已经是「点进来直接落在这封信、这一段上」的链接（§12.7），保持不变；
  其余视图参数（`class` 等）是内部的，随这次调整改
- agent 的提案卡片（M3，§12.5）在阅读区里、长在信旁边，两个区一样
- 搜索跨两区，结果标出各自属于哪个区
- 这里要新增的读路径（线程列表、分页的前缀表、计数）都带 `Viewer`，进 ACL 测试表（§13.8）：
  受限主体看到的计数也只能算它看得见的信
