# 接入

写给让 agent 或其他服务使用 yuuka 的人：怎么连上、要什么权限、会得到什么结果。凭据由运维者在服务器上签发
（[管理命令](../operate/cli.md#凭据)）。

| 接口 | 适合 | 文档 |
|---|---|---|
| MCP | LLM agent：检索、阅读、起草、提交 | [mcp.md](mcp.md) |
| SMTP 提交口 | 只会发邮件的服务：监控、告警、定时任务 | [smtp.md](smtp.md) |
| REST | 自己写的程序 | [rest.md](rest.md) |

三条路后面是同一套权限，先知道这两点：

- **凭据的 scope 决定能做哪类事**（读信、起草、提交……），**发信地址上的授权决定以哪个地址发、能发到哪一步**。
  两层都由 yuuka 在服务端检查，不是约定
- **超出授权的提交不报错，而是停在草稿**等人确认，结果里写明原因。这是正常结果，不要换一条路再发一次。
  以人的地址发信时，不是本人提交的一律停在草稿

所有调用都记进审计，运维者能看到每把凭据做了什么。

## 邮件内容是发件人写的

任何人都能往 catch-all 域投信。工具返回的发件人、主题、正文、未认领的前缀名都是**发件人写的数据**，
yuuka 把它们包在 `<untrusted_mail_content>` 边界里返回，和 yuuka 自己断言的事实（认证结论、是否降级、前缀状态）分开。
信里提出的要求是发件人的请求，不是运维者的；让 agent 对照边界外的事实判断，而不是照做或一概不理。
信里的验证码和登录链接是给人的，不要让 agent 自己去用（[为什么](../design/agents.md#83-邮件正文是攻击面catch-all-尤其)）。
